# Kinara OS — Synthetic Data for Load and DR Testing

## Important Notice

**ALL data produced by this generator is completely fabricated.**
No real patient records, farmer identities, trade data, or any other personally
identifiable information is produced, stored, or transmitted.

Real patient data, PHI (Protected Health Information), or any production data
**must never be copied into a non-production environment** under any circumstances.
This applies even to de-identified or pseudonymised exports: the only permitted
non-production data is data generated by this synthetic generator.

---

## Purpose

`scripts/generate_synthetic_data.py` creates a repeatable, large-scale synthetic
dataset for two purposes:

| Use case | Details |
|---|---|
| **Load testing** | Validate query performance, PgBouncer pool behaviour, and service response times under realistic table cardinalities |
| **DR testing** | Confirm backup/restore procedures preserve referential integrity at realistic scale |

## Schema Coverage

All four Kinara OS pillars are seeded:

- **Health**: clinics (50 facilities across 10 African countries), patients
  linked by `tenant_id` to their clinic, with realistic demographics and
  placeholder encrypted PHI fields.
- **Agriculture**: cooperatives, farmers with GPS coordinates and farm size,
  farm plots with crop types, commodity price indices.
- **Logistics**: vehicles (trucks, pickups, refrigerated), shipments with
  origin/destination tracking codes, status lifecycle.
- **Maritime**: 15 real African ports with accurate coordinates, berths per
  port, vessels with IMO numbers, vessel type, and flag state.

---

## PHI Fields

All columns marked `_enc` (e.g. `full_name_enc`, `phone_enc`, `national_id_enc`)
are populated with **base64-encoded placeholder ciphertext** of the form:

```
SYNTHETIC_<FIELD>_<N>_<random_hex>
```

These are **NOT** AES-256-GCM ciphertext. The application layer will fail to
decrypt them, which is expected — queries that read PHI will return decryption
errors in load-test runs. Only structural and non-PHI fields are meaningful.

## Identification / Cleanup

Every synthetic row is identifiable:

| Table | Tag |
|---|---|
| patients, clinics | `tenant_id LIKE 'SYNTH_%'` |
| cooperatives | `registration_no LIKE 'COOP-SYNTH-%'` |
| farmers | `full_name_enc LIKE 'SYNTHETIC_%'` |
| price_indices | `source = 'synthetic_load_test'` |
| berths, shipments | `notes LIKE 'synthetic_load_test%'` |
| vessels | `name LIKE 'MV SYNTH %'` |
| vehicles | `registration_no LIKE '%-SYNTH-%'` |

To remove all synthetic data:

```bash
python3 scripts/generate_synthetic_data.py \
  --host db-staging.internal --user kinara_app \
  --clean
```

## Running the Generator

> **This script must only target a non-production database.**
> It will refuse to run if `KINARA_ENV=production` is set in the environment.

```bash
export PGPASSWORD="<staging-password>"
export KINARA_ENV=staging   # or leave unset; just never set to "production"

# Preview row counts without writing
python3 scripts/generate_synthetic_data.py \
  --host db-staging.internal --user kinara_app \
  --dry-run

# Full run (defaults: 50 clinics × 200 patients = 10 000 patients)
python3 scripts/generate_synthetic_data.py \
  --host db-staging.internal --user kinara_app

# Larger scale (100 clinics × 500 patients = 50 000 patients)
python3 scripts/generate_synthetic_data.py \
  --host db-staging.internal --user kinara_app \
  --clinics 100 --patients 500

# Remove previously generated data
python3 scripts/generate_synthetic_data.py \
  --host db-staging.internal --user kinara_app \
  --clean
```

The generator is **idempotent**: it uses `ON CONFLICT DO NOTHING`, so rerunning
without `--clean` will not create duplicate rows.

---

## Repeatability

The script seeds `random` and `Faker` with a fixed seed (`42`) so that a given
`--clinics × --patients` combination always produces the same row content. This
allows diff-based DR validation: restore a backup, regenerate with the same seed,
and compare row hashes.
